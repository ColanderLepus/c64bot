# M2: Find Lode Runner's data in RAM

**Status:** In progress, started 2026-11-15

Find where Lode Runner keeps what the bot needs in the C64's RAM: the game's state, the level, the player, the guards, the holes, and the counters. RAM comes straight from the core after each frame (`LibretroCore.SystemRam`), and save states let us try the same moment again with different inputs. Findings go in the RAM map in [lode-runner.md](../lode-runner.md).

## Tasks

- [x] Build the RAM-compare tool (F1)
- [x] First target: the game's state (title screen, demo, playing, level ready), so start-up no longer depends on fixed frame numbers (M1 T7) (F4, F5)
- [x] Half-updated state: RAM is read when `retro_run` returns, at the end of a frame, which can fall in the middle of the game's update. Find out whether that happens, and how to read a complete state (M1 notes). (F6)
- [x] Level grid (28×16 in the Apple II original) and tile codes (F7)
- [x] Player position, including position within a tile (F8)
- [ ] Guard positions and states
- [ ] Gold remaining, lives, level number
- [ ] Hole/dig state and refill timers
- [ ] Find out how the C64 version maps digging (fire button plus direction, or keys)
- [ ] Record findings in the RAM map in [lode-runner.md](../lode-runner.md)

## Steps

Agreed with the owner on 2026-11-15. Done one step at a time, checking each before starting the next. The addresses are from the disassembly (see Notes) and are only hypotheses until a step confirms them. Generic code goes in `C64Bot.Libretro`, Lode Runner code in `C64Bot.LodeRunner` (D12).

- [x] **F1. RAM-compare tool** (in `C64Bot.Libretro`). It compares two RAM images and lists the changed address ranges with old and new values, optionally limited to chosen ranges. It saves RAM to a file and loads a `.prg` file at its load address. In the app's console, R remembers RAM and D prints what changed since then. Check: unit tests; in the demo, D shows changes where the disassembly says the moving parts are.
- [x] **F2. Is version A the original?** Compare version A's `$6000`–`$B7FF` during a level with `it` from our own disk (version B) and with the disassembly's `it.prg` (kept outside the repo). Check: every difference is explained (the trainer's patches, the removed copy protection, code that changes itself). Then write the disassembly's map into `lode-runner.md`, marked unconfirmed. If version A differs widely, stop and fall back to searching RAM with F1.
- **F3. Trace addresses per frame.** Dropped (owner's call, 2026-11-15): it was meant for searching, and the disassembly already says what the bytes mean. F4 prints the bytes it uses instead. Bring it back if a state can't be told apart with the bytes we know.
- [x] **F4. Game state.** `GamePhaseReader` in the new `C64Bot.LodeRunner` reads a `GamePhase` after every frame: `Other` (until the game's interrupt routine is in place, or the level editor), `Title`, `Demo`, `LevelStarting` (everything between two stretches of play while the player is alive), `Playing` (the main loop runs: the interrupt counter `$132D` keeps dropping back to 3–5), `Dying` (dead during play, lives left) and `GameOver` (dead, no lives left). A completed level shows as the level number `$1305` going up. The app prints each phase change and each level number. Check: a headless run to game over gives the phases in the right order; then the owner plays (title, demo, SPACE, first move, caught, C= skip) and the printed changes match the screen. Changed during the step (owner's go-ahead, 2026-11-15): level complete was dropped as a phase, because RAM doesn't tell it apart from setting up the next level, and nothing needs it; F3's trace was dropped, so the app prints the bytes instead.
- [x] **F5. Start-up and level picking.** `GameStarter.Start` runs flat out from loading through the trainer menu into the running demo, presses SPACE, and saves a state in memory at the first frame of the new game, before it loads its level. `StartLevel(n)` loads that state and writes the level number (`$1310` = n − 1, `$1305` = n), so the game loads level n itself (D13). For that, `LibretroCore.WriteSystemRam` writes RAM. The app starts at the level given on its command line, level 1 if none. Check: the tests pass (level 5 after level 1 gives a different grid and the right numbers); headless, the times and levels 1, 5 and 150; the owner runs the app with `-- 5` and level 5 plays normally. Changed (owner's go-ahead, 2026-11-15): first planned as start-up only, then combined with picking a level.
- [x] **F6. Half-updated state.** Measured headless instead of in VICE (owner's go-ahead, 2026-11-15): a throwaway script read the CPU's PC from the save state after every frame, in the demo and on levels 5 and 150, and counted what was half done (see Notes). Most frames end inside a pass, but little is half done, so the owner chose no fix: each thing is read from where it's always complete (D14, "Reading RAM" in `lode-runner.md`). The readers in F7–F9 follow the rules, and their checks cover them.
- [x] **F7. Level grid.** 28×16, one byte per tile, at `$0800` (as played, with holes) and `$0A00` (as built); rows 0–8 at `base + 28 × row`, rows 9–15 four bytes later. Tile codes 0–9: empty, brick, solid block, ladder, rope, trap brick, exit ladder, gold, guard, player. Hidden exit ladders at `$1200`/`$1230`, their count at `$1301`. Check: the grid as text for level 1 and two other levels matches the screen; digging changes `$0800` only; the exit ladders appear when all gold is taken. Built as `Level`, `Tile` and `TilePosition` in `C64Bot.LodeRunner`, read from the grid as built (D14), and console key G in the app. Checked headless by Claude on all 150 levels and against saved pictures (see Notes).
- [x] **F8. Player.** `$03`/`$04` column and row, `$05`/`$06` position within the tile (0–4, 2 = centre), `$07` sprite (facing and action), `$1315` falling, `$1316` digging. Check: walking, climbing, the rope, falling and digging show in the printed values. Built as `Player` (with `Pose` and `Direction`) and the first part of `GameState` in `C64Bot.LodeRunner`: `GameState.TryRead` reads the level and the player, or gives false for a frame to skip (D14), and `GameState.ToString` draws the level as on screen, so far with the player (owner's choice, 2026-11-15: `Level.ToString` stays the layout; `GameState` grows with the guards in F9 and the holes in F10). The app's G key prints the game state. Checked by Claude, headless, against saved pictures (see Notes).
- [ ] **F9. Guards.** Count at `$131C`; guard n (1–5) in tables at `$1260+n` (column), `$1268+n` (row), `$1270+n` (negative: carries gold, counts up to 0 and drops it; positive: stuck in a hole, counts down), `$1278+n`/`$1280+n` (position in the tile), `$1288+n` (sprite), `$1290+n` (facing), `$1298+n` (respawn timer). Check: a guard picks up gold, falls into a hole, dies and respawns, all in the printed values; confirms the respawn rule.
- [ ] **F10. Holes and counters.** Holes at `$12A0` (column), `$12C0` (row), `$12E0` (timer: 180 passes, about 6 s; refilling in stages at 20 and 10), up to 30; lives `$1312`, level `$1305` (1–150), score `$130A`–`$130D` (BCD, lowest byte first). Check: dig on both sides, lose a life, take gold, skip a level, and the values follow. Write down how digging is controlled.
- [ ] **F11. Finish.** The RAM map in `lode-runner.md` is complete, with how each entry was confirmed.

## Notes

- **F1, first comparison** (headless, 2026-11-15): in the demo (`$1306` = 1, 3 guards, `$131C` = 3), RAM was compared one second (50 frames) apart. Changes were where the disassembly says: the zero page (55 bytes), the guard tables (`$1261`–`$129B`: column, row, gold/hole timer, position in the tile, sprite, facing `FF` → `01`, respawn timer), a hole timer (`$12E2`: `8F` → `70`, 31 passes in 50 frames, so about 30 passes a second), joystick X (`$131A`: `22` left → `2A` right, the demo's moves), the guard respawn column (`$131E`: `17` → `1A`, one step per pass, wrapping at 28), the interrupt counter (`$132D`), single grid bytes at `$0800` turning to or from 8 (guard) and 9 (player), sprite data at `$0C00`, small parts of both hires screens, one byte of code that changes itself (`$8C19`) and the sound buffer (`$C00C`). Also the stack (`$01E8`–`$01F8`).
- **F1, in the app** (the owner, 2026-11-15): R at frame 1036 and D at frame 1120 in the demo, while the demo player picked up a piece of gold. Gold left (`$130E`) went `0E` → `0D`; the score (`$130A`–`$130B`) went `00 00` → `50 02`, BCD 250 with the lowest byte first, the points for one gold; and the gold's tile at row 14, column 7 went `07` → `00` in both grids (`$0993` as played, `$0B93` as built), which fits rows 9–15 starting 4 bytes later. Code that changes itself showed up at `$7A95`–`$7AA1`, `$8B1D`–`$8B40` and `$8C19`.
- **F2** (headless, 2026-11-15): version A in level 1 differs from the disassembly's `it.prg` in 22 of 22,528 bytes, and version B's `it` (extracted with `c1541`) from `it.prg` in 4. All are explained: the trainer's three changes, and code that changes itself. Details in [lode-runner.md](../lode-runner.md) (The disassembly, Trainer), along with the disassembly's RAM map. A throwaway script in the scratchpad did the comparison, with `PrgFile` and `RamImage`; nothing for it was added to the repo.
- **F4, the first rules** (headless, 2026-11-15) had three problems. Before the game runs, the bytes are leftovers, so loading and the trainer menu gave random phases. "Level complete" (main loop stopped, no gold left) also matched while a level is set up, because setting up sets the gold count to 0 and counts it up again; and the C= skip reaches level complete with gold left. And right after SPACE in the demo the player is dead with 5 lives for 17 frames (the demo ends by killing its player, and the new game gives him his lives first), which looked like a death. Also, a short joystick tap while a level starts can come too early, because RAM doesn't show when the level is ready; a move held through `LevelStarting` always worked.
- **F4, headless to game over** (2026-11-15, N to both trainer questions, SPACE in the demo, a move held through each `LevelStarting`, otherwise standing still): `Other` until frame 2920, `Title`, `Demo` from 3292, `LevelStarting` from 4034, `Playing` from 4678, then 5 times `Dying` (11–12 frames) and `LevelStarting` (885 frames) as the guards caught the player about 247 frames into each try, lives going 5 → 0, then `GameOver` at the last death (frame 9497) and `Title` 834 frames later.
- **F4, in the app** (the owner, 2026-11-15, Y/N): `Title`, `Demo`; SPACE gave `LevelStarting` and level 1; the first move gave `Playing`; caught: `Dying` for 12 frames, then `LevelStarting`, lives staying at 5; C= gave level 2 at once and `LevelStarting` 5 frames later (the reader's allowance for noticing the main loop has stopped), with lives 5 → 6 and 5 gold still left, as the trainer's hook goes through the game's own "level complete".
- **F5, headless** (2026-11-15): `Start` took 3,531 frames, 5.4 s flat out. Then `StartLevel` for levels 1, 5, 150 and 2: each reached `Playing` about 640 frames (0.9 s) later, with `$1305`/`$1310` as written, 5 lives, score 0, and each level's own gold and guards (level 150: 50 gold, 5 guards). The first try pressed SPACE as soon as the phase was `Demo`, and the new game never came: SPACE only counts once the demo runs, so `GamePhaseReader` now tells whether the main loop runs (`MainLoopRunning`), and `Start` waits for that. Level 2 got no input at all and still started: a level waiting for its first move also starts on any key waiting in `$1328`, and the SPACE that starts a new game is still there. That's what any new game does, so it was left that way. SPACE has to be up in the C64's keyboard before the state is saved, or it stays held in every game started from it, so `Start` releases it and runs 2 frames first.
- **F5, in the app** (the owner, 2026-11-15, `-- 5`): start-up in 5.3 s; level 5 came up and started by itself at frame 643; the owner took 6 of its 7 gold, was caught at frame 3015, and the level waited in `LevelStarting` again.
- **F6, where frames end** (headless, 2026-11-15, a throwaway script; random joystick input in the levels): the CPU's PC at the end of each frame, read from the save state (the VICE core saves VICE's snapshot format, whose `MAINCPU` module holds the registers; saving a state costs about 0.07 ms), and for frames that end in the interrupt, the interrupted PC from the stack. Counted over frames with the main loop running:

  | | Demo, 3 guards | Level 5, 4 guards | Level 150, 5 guards |
  | --- | --- | --- | --- |
  | Frames measured | 6,000 | 3,000 | 3,865 |
  | Frame ends in a pass (including interrupted passes) | 55% | 62% | 62% |
  | Frame ends in the interrupt routine | 2% | 2% | 2% |
  | The guard being moved (`$131F`) differs from his table entry | 11% | 13% | 15% |
  | A guard's table entry has no guard tile in the grid, in a pass | 3% | 4% | 3% |
  | No player tile in the grid at `$03`/`$04` | 0.1% | 0.03% | 0.03% |

  Most of a pass's time is spent at `$80xx`–`$8Dxx`, which by its place in the source is drawing. The guard tables are written in one go after a guard's move (`EnemyMoveStatusSave`), so they're always complete, but up to one move behind for the guard being moved; the grid's guard tiles can be ahead of them. In the demo, 1.5% of frames in the wait also had a guard without a guard tile, so that's a game situation, not a half update.
- **F7, where the game writes the grids** (from the disassembly): digging writes only the grid as played (`$0800`): a hole is an empty tile there, while the grid as built (`$0A00`) keeps the brick. Gold taken, picked up by a guard or dropped changes the grid as built. The exit ladders are written to both, as plain ladders (3). So during play the grid as built holds only codes 0–5 and 7, and holes have to come from the hole tables (F10).
- **F7, all 150 levels** (headless, 2026-11-15, each read at the first frame of `Playing`): only known tile values; the gold tiles add up to `$130E` on every level; the grids differ only at the player and guards; no hidden ladder is on anything but an empty tile. 39 levels have no hidden ladders, and at least one has 45, the most the game keeps. The level 1 picture matched the game's level 1.
- **F7, against the screen** (headless, 2026-11-15, with the core's pictures saved as PNG files and compared by Claude, so the owner needn't test by hand): `Level`'s text for levels 1, 5 and 150 matched the pictures. On level 1, fire made a hole at (13,15), which showed only as a difference between the grids (built 1, played 0) and as a gap in the bricks in the picture. A guard picked up a gold: it left the grid as built, and the gold counter stayed at 6. With the gold counter set to 0 (a shortcut in the check script, not in the bot), the game showed the exit ladders on its next pass: column 18, rows 0–3 became ladders in the grid as built and in the picture, and the counter became `$FF`. The player was facing right but dug to his left: see F10.
- **F8, the player against the screen** (headless, 2026-11-16, scripted joystick on level 2, after two tries on level 1 where a guard caught him on row 12): at each point the `GameState` text and the player's values matched the saved picture. Walking right from column 12 and climbing the ladder in column 21: pose `Ladder`, no facing. Along the rope on row 11: `Rope`, facing left. Dropping off at column 18: `Fall`, `Falling` true, three frames later at the top of row 12 (offset −2); landed on row 14: `Falling` false, the pose still `Fall` until he moves. Fire: `Dig`, facing and digging left. On level 1, walking right picked up the gold at (17,14).
- **F8, how often a frame is skipped** (headless, random joystick, 10,000 frames of `Playing` each): 1 on level 5, 2 on level 150, so 0.01–0.02%. Twice the step was `$FF` for a moment (the game counts down past 0 before changing the column), once the player was between two rows while falling.
- **Getting past the trainer menu** (was an open question in `PLAN.md`): `GameStarter` types the answers once per session, flat out (5.4 s), and every new game starts from its state in memory. Files aren't needed for now.

- **A disassembly of the C64 original exists:** [Piddewitt/Loderunner](https://github.com/Piddewitt/Loderunner) on GitHub, "reverse engineered C64 assembler source code to recreate a bit for bit identical version of the original game", with labelled zero page (`inc/LR_ZPG.asm`), game variables (`inc/LR_Var.asm`) and the main program (`asm/it.asm`, loaded at `$6000`). Found 2026-11-15. Its routine `IRQ` starts with the same bytes that version A has at `$648A` (`EE 2D 13`, `INC $132D`), so version A runs the original's code at the original's addresses (to be checked over the whole program). Some of the addresses in its comments don't match its own definitions (for example the hole tables), so addresses are worked out from the definitions.
